# Кастомная система аутентификации и авторизации (RBAC) на Django REST Framework

Проект представляет собой бэкенд-приложение с собственной независимой системой разграничения прав доступа к ресурсам. Логика контроля доступа разработана с нуля и не использует встроенные механизмы Django (`contrib.auth` группы и разрешения).

## 🌀 1. Схема базы данных и архитектура доступа

В основе системы лежит модель **RBAC (Role-Based Access Control)**, расширенная до контроля операций над конкретными ресурсами. Доступ предоставляется на основе матрицы: **Роль -> Ресурс -> Действие**.

### Описание сущностей (Таблиц БД)

1. **User (Пользователи)** — хранит базовые профильные данные (`first_name`, `last_name`, `email`), хэш пароля и флаг мягкого удаления (`is_active`).
2. **Role (Роли)** — справочник ролей в системе (например: `Admin`, `User`).
3. **UserRole (Связь пользователей и ролей)** — таблица связи Many-to-Many. Позволяет назначать пользователю одну или несколько ролей одновременно.
4. **Resource (Ресурсы)** — системные сущности или эндпоинты, доступ к которым необходимо ограничивать (например: `documents`, `permissions`).
5. **Action (Действия)** — типы операций над ресурсами (`read`, `create`, `update`, `delete`).
6. **Permission (Разрешения / Матрица доступа)** — ключевая связующая таблица. Определяет, какая **Роль** имеет право совершать определенное **Действие** над конкретным **Ресурсом**.

### Диаграмма связей

```text
[User] ── (1:N) ──> [UserRole] <── (1:N) ──> [Role]
                                               │
                                             (1:N)
                                               ▼
                                         [Permission]
                                         ├── Resource (FK)
                                         └── Action (FK)
```


## 🛠️ 2. Алгоритм работы разграничения прав

1. **Идентификация (401 error)**: Кастомный middleware/authenticator (`CustomJWTAuthentication`) проверяет заголовок запроса `Authorization: Bearer <token>`. Если токен отсутствует, поврежден или срок его действия истек — возвращается HTTP-ответ `401 Unauthorized`.
2. **Авторизация (403 error)**: Кастомный класс ограничений (`CustomRBACPermission`) динамически принимает параметры запрашиваемого ресурса и действия. Он собирает все роли залогиненного пользователя и проверяет их наличие в таблице `Permission`. Если явного разрешения на связку `Ресурс + Действие` для ролей пользователя в БД нет — возвращается HTTP-ответ `403 Forbidden`.

## 🚀 3. Тестовая матрица доступа и результаты тестирования (Чек-лист API)

В системе развернуты демонстрационные правила доступа, которые были успешно верифицированы в ходе ручного тестирования через Postman.

### 🟢 Позитивные сценарии (Счастливые пути)


| Метод | Эндпоинт | Описание тест-кейса | Роль / Токен | Статус ответа |
| :--- | :--- | :--- | :--- | :--- |
| **POST** | `/api/auth/register/` | Регистрация нового пользователя | Аноним (Без токена) | **`201 Created`** |
| **POST** | `/api/auth/login/` | Авторизация пользователя, генерация JWT | Аноним (Свежие креды) | **`200 OK`** |
| **PUT** | `/api/auth/profile/update/` | Редактирование профиля текущего юзера | Любая роль (Валидный JWT)| **`200 OK`** |
| **POST** | `/api/auth/logout/` | Выход пользователя из системы | Любая роль (Валидный JWT)| **`200 OK`** |
| **DELETE**| `/api/auth/profile/delete/` | Мягкое деактивирующее удаление аккаунта | Любая роль (Валидный JWT)| **`200 OK`** |
| **GET** | `/api/business/documents/` | Успешный просмотр Mock-документов | Роль `User` или `Admin` | **`200 OK`** |


### 🔴 Негативные сценарии (Проверка безопасности и отказоустойчивости)

| Метод | Эндпоинт | Описание тест-кейса | Роль / Токен | Статус ответа |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | `/api/business/documents/` | Запрос закрытого ресурса без авторизации | **Аноним (Без токена)** | **`401 Unauthorized`** |
| **GET** | `/api/business/documents/` | Запрос закрытого ресурса со старым токеном | **Просроченный/Битый JWT** | **`401 Unauthorized`** |
| **POST** | `/api/admin/permissions/` | Попытка обычного юзера изменить правила прав | Роль **`User`** (Валидный JWT) | **`403 Forbidden`** |
| **GET** | `/api/permissions/` | Обращение к несуществующему адресу (битый URL)| Любой запрос | **`404 Not Found`** |

## 💻 4. Быстрый запуск проекта

### 1. Установка зависимостей
Убедитесь, что ваше виртуальное окружение активировано, и выполните установку библиотек вместе с драйвером базы данных PostgreSQL:
```bash
pip install django djangorestframework PyJWT psycopg2-binary
```

### 2. Применение миграций (Создание таблиц в PostgreSQL)
```bash
python manage.py makemigrations auth_app
python manage.py migrate
```

### 3. Наполнение базы тестовыми данными (Матрица доступа)
Запустите интерактивную консоль Django:
```bash
python manage.py shell
```
Скопируйте и выполните внутри консоли следующий код:
```python
from auth_app.models import Role, Resource, Action, Permission
admin_role, _ = Role.objects.get_or_create(name='Admin')
user_role, _ = Role.objects.get_or_create(name='User')
doc_res, _ = Resource.objects.get_or_create(name='documents')
perm_res, _ = Resource.objects.get_or_create(name='permissions')
read_act, _ = Action.objects.get_or_create(name='read')
update_act, _ = Action.objects.get_or_create(name='update')
Permission.objects.get_or_create(role=admin_role, resource=doc_res, action=read_act)
Permission.objects.get_or_create(role=admin_role, resource=perm_res, action=update_act)
Permission.objects.get_or_create(role=user_role, resource=doc_res, action=read_act)
exit()
```

### 4. Запуск сервера разработки
```bash
python manage.py runserver
```
Интерфейс API будет доступен по локальному адресу вашего компьютера: `http://127.0.0`

## 📡 5. Основные эндпоинты API

* `POST /api/auth/register/` — Регистрация нового пользователя (автоматически присваивается роль `User`).
* `POST /api/auth/login/` — Аутентификация по email и паролю. Возвращает свежий JWT-токен.
* `PUT /api/auth/profile/update/` — Обновление информации (редактирование профиля текущего пользователя).
* `POST /api/auth/logout/` — Выход пользователя из системы (сброс сессии).
* `DELETE /api/auth/profile/delete/` — Мягкое удаление профиля текущего пользователя (флаг `is_active=False`).
* `GET /api/business/documents/` — Mock-View бизнес-объектов (доступно по матрице для ролей `Admin` и `User`).
* `POST /api/admin/permissions/` — Управление правилами авторизации (доступно строго для пользователей с ролью `Admin`).
